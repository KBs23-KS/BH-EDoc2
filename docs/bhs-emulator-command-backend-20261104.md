# BHS E-Document — emulator-only command backend (4 Nov 2026)

**Stage 1 implementation in a new stacked Draft PR. No production deployment, no Firebase connection, and NO actual PDF signing.**

## What has been implemented

- security-test/backend/emulatorCommandService.mjs: a command processor limited to the demo-bhs-realistic-only Firestore Emulator on localhost port 8099. It receives a Firebase ID token via a required verifier, validates the identity claim, loads the CURRENT active user and role from Firestore, reads current settings/recipients, evaluates the BHS-shaped policy, and writes the document and independent audit log atomically within a Firestore Admin transaction.
- security-test/backend/loopbackHttp.mjs: HTTP-only test adapter, bound by the test harness to 127.0.0.1, requiring POST JSON + Bearer token and rejecting cross-origin requests. Deliberately not a Vercel API endpoint and has NO public deployment config.
- tests/bhs-emulator-backend-integration.mjs: end-to-end HTTP tests with local Firebase Admin Firestore Emulator and **synthetic mock token verifier**. Test tokens are never usable with Firebase Authentication.
- Commands include create-incoming, deputy-review, return-correction, resubmit-revision, director-publish, director-route, head-forward (including broadcast and reassignment), acknowledge-document, acknowledge-assignment and check-sign-pdf.
- Untrusted clients cannot provide arbitrary Firestore field updates or change their own user role. Recipient IDs and fake PDF references are validated. Audit log entries are generated by the server, alongside changes.
- check-sign-pdf is permission checking ONLY; no signedFiles modification, PDF rendering or Drive calls.

## Mandatory fail-closed boundary

The backend constructor refuses to run unless process.env.FIRESTORE_EMULATOR_HOST equals 127.0.0.1:8099 and the Firebase Admin app projectId equals demo-bhs-realistic-only. This is NOT a production backend and has deliberately not been wired to src/App.jsx, /api, the production Vercel project, or the existing isolated security Preview.

The mock verifier is used ONLY within the integration test. A production API must use a real Firebase Admin verifyIdToken implementation, secure credentials and datastore, consistent user role/claims/revocation, rate limits, CSRF/origin policy, least-privilege controls, and a controlled migration. Copying this file into a production app would be unsafe.

## Test commands

Run with GitHub Actions (pull_request targeting the prior test branch):
- node tests/bhs-realistic-workflow-policy-test.mjs
- Firebase Emulator test: tests/firestore-bhs-realistic-emulator.mjs
- npx --yes firebase-tools@14 emulators:exec --project demo-bhs-realistic-only --config security/firebase-bhs-realistic.emulator.json --only firestore "node tests/bhs-emulator-backend-integration.mjs"

The emulator suite tests user roles, current inactive status, invalid/revoked tokens (fake stub), forged role/metadata, multiple-document transitions, corrections and PDF version history, acting head delegation, subject-head broadcast, duplicate acknowledgement, signed PDF eligibility, and atomic audit creation. No actual Firebase service or real records are contacted.

## Still required before a production fix

1. Isolate/secure existing credential storage. Current live browser preloads plaintext legacy passwords and uses anonymous Firebase sign-in. Stage 1 does not change this.
2. Implement actual production API identity handling and secure directory without breaking existing usernames/passwords, with a plan for migration and rollback.
3. Replace collection-wide Firestore listeners with authorised read APIs or carefully designed queries and indexes.
4. Implement real PDF signing/Drive permissions and verify signing records, numbers, revision histories, head multi-group assignments, and audit integrity end-to-end.
5. Run a full staging cutover rehearsal with fresh backup/restore, all role tests and manual acceptance on iPad/desktop.
6. Only then separately authorize the production roll-out.
